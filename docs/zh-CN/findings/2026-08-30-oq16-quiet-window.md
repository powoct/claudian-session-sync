# 2026-08-30 · OQ-16:静默窗口该取多大——把 OQ-17 的采样重新读一遍就有答案

> 没有新做实验。OQ-17(2026-08-27)在开发机上用 100 ms 采样器录过**两轮完整的 Grok turn**,
> 当时只用它回答「流式期间会不会就地重写」,数据本身一直还在(`tmp/notes/oq17-run*.json`,不入库)。
> 这次换个问法重读:**一个正在出字的会话,最长能整组静止多久?**

## 结论:出厂默认 3000 ms 太小,即使在 ADR-58 之后

ADR-58 把稳定性判定从「单个文件」改成「整组文件的合成签名」,理由是成员之间的静默是错开的——
`chat_history.jsonl` 在 turn 中途静止 23 秒时,`events.jsonl` 走了约 90 个版本。那条修法是对的。
但它没有回答**合成之后还剩多长的静止**,而那才是窗口取值要对付的东西。

把两轮里所有非 `.lock` 文件的变化时刻合并(这正是 group 见证签名会看到的):

| | 变化时刻数 | 采样跨度 | **最长合并静止** |
|---|---|---|---|
| run 1 | 30 | 7,716 ms | **3,344 ms** |
| run 2 | 101 | 23,520 ms | **8,212 ms** |

对照几个候选窗口——「被骗」指静止期长到足以让该窗口判定为「已稳定」:

| 窗口 | run 1 | run 2 |
|---|---|---|
| **3,000 ms(出厂默认)** | 被骗 1 次 | **被骗 2 次** |
| 8,000 ms | 0 | 被骗 1 次 |
| **15,000 ms** | 0 | 0 |
| 30,000 ms | 0 | 0 |

**⇒ 默认改为 15,000 ms。** 两轮实测都清空,且有余量。

### 逐文件的数字(顺带,解释了为什么必须看合并值)

| 文件 | run 1 最长静止 | run 2 最长静止 | run 2 版本数 |
|---|---|---|---|
| `chat_history.jsonl` | 7,306 ms | **23,216 ms** | 3 |
| `updates.jsonl` | 3,445 ms | 14,302 ms | 6 |
| `events.jsonl` | 3,344 ms | **8,212 ms** | 96 |

**关键的一行是 `events.jsonl`**:它是全场最忙的文件(23 秒 96 个版本、中位间隔 101 ms),
也是 group 见证里最活跃的那个——**连它都有 8.2 秒的静止**。所以合并静止不是被某个懒文件拖长的,
是整个会话真的停了。ADR-58 之后仍需要一个像样的窗口,原因就在这里。

## 代价几乎为零

- **自动 pass(默认 5 分钟)**:窗口从不生效——下一轮无论如何都在 300 秒之后。改大不影响。
- **手动 Sync now**:只有在一次 turn 结束后 15 秒内点,才会多 defer 一轮。
  而「turn 刚结束 5 秒就同步」恰恰是最该 defer 的时刻。

## 不保证什么(照抄 §9.1.5,因为它仍然成立)

窗口是**启发式**,不提供互斥保证。ADR-58 早就写明:平台期有多长由模型出字速度决定、**没有上界**,
所以任何固定窗口都可能被更长的停顿穿过。两轮样本也只是两轮。
这个数字买到的只是:**已实测到的平台期不再塞得进窗口里**。
真正的数据保护仍然是验证式覆盖、覆盖前备份,以及冲突两侧都留。

## 未覆盖

- `remoteQuietMs`(8,000 ms)**没动**:它对付的是同步工具往 replica 里写,是另一种现象,本轮无数据。
- 采样只有 Grok。Claude Code / Codex 是单文件、实测严格追加,不声明见证文件,
  它们的窗口行为没有对应测量——但它们也没有「成员之间静默错开」这个问题。
- 两轮都是同一台开发机、同一个模型。换机器、换模型速度,平台期会变。
