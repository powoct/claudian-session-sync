**compact 缺口(OQ-13,发布阻塞)**:codex 0.146.x 没有非交互 compact 入口
(`exec`/`debug` 均无,`/compact` 仅存在于 TUI);macOS 上两次用 pty 驱动 TUI 发
`/compact` 均未生效(快照证明文件零变化——是没执行,不是执行后无痕);Windows 环境
无 TTY。**需人工在 TUI 里补测一次**(约 5 分钟:resume 测试会话 → `/compact` →
`node lifecycle-snapshot.mjs snap` → `report`)。

**若 compact 是就地改写,风险边界已知**(引擎防线兜底,不会静默丢数据):
非前缀改写 → 分歧 → CONFLICT + 隔离(双分支保全);缩短为旧内容前缀 → 对端更长 →
PULL_OVERWRITE 把 compact 前的长版本拉回来(带备份,等于 compact 被撤销)。两种都
可恢复,但都是不该有的用户体验——所以补测是发布门禁,不是形式。

**Tier 判定:Codex Tier A 成立,附「compact 待补测」尾巴;BRAT 发布前必须清掉
(OQ-13)。** adapter 保持 experimental 标签与默认关闭。

## P1 · Codex 布局(双平台一致)

- 文件名形态**只有一种**:`rollout-<prefix>-<uuid>.jsonl`(mac 82 个 + Windows 27 个,
  外加 mac 的 3 个 `.DS_Store` 噪音,白名单天然拒收)。**冒号 0、非 ASCII 0**——
  路径字符集规则不会在任何平台拒收 Codex 会话,此前的 Windows 疑虑排除。
- 目录严格 `YYYY/MM/DD` 三层,无更深更浅(depthHistogram 双平台佐证)。
- 两台机器 `HOME` / `USERPROFILE` / `os.homedir()` 均指向同一 `~/.codex`,
  **分叉场景实测不存在于当前两台机器**(Git Bash 的 HOME 与 USERPROFILE 同值)。
  `CODEX_HOME` 均未设置。
- 首行 `session_meta.payload` 含 `cwd`、`cli_version` ✅。
- **计划外发现:subagent 线程的 rollout 也落在同一 sessions/ 树里**(首行含
  `source.subagent.thread_spawn`、`forked_from_id`、`parent_thread_id`)。
  记录准入下它们不会被同步(subagent thread id 不出现在会话记录里)——**跨机 resume
  一个用过 subagent 的会话时,子线程历史在对端缺失**。影响未知,列入下次验收观察项。

## P3 · Claudian vault 记录(实测形状核对 ADR-46/47)

两台 vault 的 `.claudian/sessions` 内容**完全相同**(78 meta / 25 inputs / 3 deleted;
codex 50、claude 17、grok 6、opencode 4、pi 1)——与「两 vault 分属不同网盘不互通」
并存的原因是人工拷贝过(2026-08-10 验收的附加验证)。

- 后缀正好三种(`.meta.json` / `.inputs.json` / `.deleted.json`),无第四种 ✅
- 无 `<unparsable>` ✅;旧版 `.claude/sessions` 两台都不存在
- **id 可用率:53/78(68%)。25 条(codex 19、claude 6)`sessionId` 为 null**,
  插件找不到它们对应的 CLI 文件 → 这些会话不参与同步(fail-closed,符合设计)。
  成因未查(疑为旧版 Claudian 未记 id,或会话未产生首轮)。**README 须写明**:
  记录里没有 session id 的旧会话不同步;在 Claudian 里继续该对话一轮通常会补上 id。
- **reader 的三选一读取被证实必要**:53 条含 `providerState` 的记录里只有 31 条有
  `threadId`——假设「总有 providerState.threadId」的实现会漏掉 22 条。本插件以
  `sessionId` 为主、`threadId`/`providerSessionId` 为辅,与实测分布一致 ✅

## P4 · Grok / Pi

- **Grok(双平台一致)**:每 session 一个目录,内含 **10+ 个文件**:
  `chat_history.jsonl`、`events.jsonl`、`updates.jsonl`、`rewind_points.jsonl`、
  `summary.json`、`system_prompt.txt`、`prompt_context.json`,以及 4 对 **`.lock`**
  文件;部分会话另有 `signals.json` 等。父目录名确认为 urlencode 的 cwd
  (机器相关)。→ **多文件 session group + 锁文件并存**,需要 §6.6 的 group 原子性
  与更谨慎的稳定性判定;比 2026-08-12 源码调查(Claudian 只读 updates.jsonl)
  显示的更复杂。M3 再议,维持 Tier C。
- **Pi**:两台机器都是「装了但无会话数据」→ 结构无从确认,维持 Tier C,OQ-6 继续挂起。

## P5 · 规模与耗时(OQ-7 → ✅ 当前规模下关闭)

| 机器 | provider | files | total | largest | walk | stat | 全量 hash 估算 |
|---|---|---|---|---|---|---|---|
| mac | claude-code | 41 | 49.4 MiB | 9.8 MiB | 2ms | 1ms | ~58ms |
| mac | codex | 85 | **183 MiB** | **23 MiB** | 1ms | 7ms | ~155ms |

| win | codex | 27 | 32.8 MiB | 7.8 MiB | 1ms | 1ms | ~29ms |

**判定:当前规模(百文件/百 MiB 级)下,每轮 pass 即使全量 hash 也在亚秒级;
遍历与 stat 在 10ms 量级。OQ-7 关闭**(若将来出现 GB 级/千文件级 vault 再重开)。

**直接行动**:实测最大 rollout 23 MiB > 旧默认 `maxFileSizeMB = 20`——该会话在
旧默认下会被 SKIP_TOO_LARGE 静默跳过。**默认已调到 64**(上限 512 不变,报告里
本就可见 SKIP,但默认值不该把常规会话挡在外面)。
