# 2026-09-01 · Claudian 2.2.5 把新会话记录挪进 `devices/`,准入静默失效

> 起因是用户报告「mac mini 上有个会话同步不过去」。验收会话的诊断报告见
> `tmp/2026-09-01-claudian-devices-layout.md`(不入库)。本文只记**对着上游源码复核后**的结论
> ——报告是从压缩过的 bundle 里提常量,而 2.2.5 的源码就在本机(`/home/code-server/projects/claudian`),
> 有几处只有源码答得了,其中一处报告明说「需向上游确认」。

## 一、上游改了什么(源码复核)

`src/core/bootstrap/storagePaths.ts`:

```ts
export const SESSIONS_PATH        = '.claudian/sessions';
export const DEVICE_SESSIONS_PATH = `${SESSIONS_PATH}/devices`;   // 2.2.5 新增
export const INPUT_LEDGER_SUFFIX  = '.inputs.json';
export const DELETION_MARKER_SUFFIX = '.deleted.json';
export const ASSIGNMENT_MARKER_SUFFIX = '.assigned.json';         // 2.2.5 新增
```

`SessionStorage.ts` 里每类文件各自落在哪一层,**不是一刀切**:

| 文件 | 路径 | 层 |
|---|---|---|
| `.meta.json`(新建) | `getMetadataPath` → `devices/<deviceKey>/` | **设备层** |
| `.meta.json`(存量) | `getUnscopedMetadataPath` → `sessions/` | 顶层 |
| `.meta.json`(更旧) | `getLegacyMetadataPath` → `.claude/sessions/` | legacy |
| `.inputs.json` | `ConversationInputLedgerStorage` 用 `SESSIONS_PATH` | **只在顶层** |
| `.deleted.json` | `getDeviceDeletionMarkerPath` **与** `getUnscopedDeletionMarkerPath` | **两层都有** |
| `.assigned.json` | `getAssignmentMarkerPath` → `SESSIONS_PATH` | **只在顶层** |

⇒ 报告说的「同一个 conv 的 `.meta` 与 `.inputs` 被拆到两层」属实,已核。
设备 key 的形状是 `/^device-[a-f0-9]{64}$/`(`InstallationKey.ts`)。

### 墓碑的跨层语义(报告说「需向上游确认」,源码里写着)

`selectSessionMetadataCandidate()` 逐条:

```ts
if (assignment.status === 'invalid') return null;
if (assignment.status === 'assigned') {
  if (assignment.deviceKey !== deviceKey) return null;   // ← 指派给别的设备 ⇒ 本机不可见
  ...
}
if (deviceMetadataPath && !deviceDeleted)   return device;
if (unscopedMetadataPath && !unscopedDeleted) return unscoped;
if (legacyMetadataPath  && !unscopedDeleted) return legacy;
```

**墓碑按层配对**:`deviceDeleted` 只压设备层,`unscopedDeleted` 压顶层与 legacy。
一个设备的删除**不会**埋掉顶层的同名记录,顶层的墓碑也**不会**埋掉设备层的记录。
本插件照抄这条规则,而不是近似它——跨层配对会让一台机器的删除隐藏另一台仍持有的会话。

## 二、本插件为什么静默失效

`readVaultScope()` 对 store 只做单层 `listDir` 且 `if (!entry.isFile) continue`,
`devices/` 作为目录项被直接丢掉。被丢掉的会话**根本没进候选集**,于是:
不产生 report 行、不触发 Notice、状态栏照常 `up to date`。
而顶层还有 111 条存量记录,`storeFound` 仍为 `true`,连 healthCheck 都不会响。

**四个 provider 共用 `readVaultScope()`,所以全部受影响**,不是 claude-code 专属。

## 三、修法与一个刻意的分歧

两层、且目录名按上游的 `device-<64hex>` 校验(不做无限递归——§8.2 fail-closed)。

**一个刻意与上游不同的地方:本插件读取所有设备目录,不只是本机那个。**

上游的列表是**按设备作用域**的(见上面的 `assignment.deviceKey !== deviceKey ⇒ null`),
「Assign to this device」按钮就是干这个的。但准入回答的是另一个问题——**这个 vault 认不认识这个
session id**。若也按设备作用域,那么 Mac 上新建的会话**永远无法把字节搬到 Windows**,
而那正是本插件存在的唯一理由。所以:**准入放行,由 Claudian 自己决定显示什么。**

## 四、没做的事,以及为什么

### `claudian` provider 自身(默认关闭)仍不认识设备层

诊断报告 6.2 建议一并修 `listSessions`/`targetPathFor`/`neutralRel`。**本轮没做**,理由是它需要一个
真正的设计决定而不是顺手改:

- 该 provider 的 `logicalId` 是**按文件**的(`conv-x.meta` 与 `conv-x.inputs` 是两个 group,ADR-48),
  而**同一个 conv 可以同时存在于顶层与设备层**(上游的候选选择器整段就是在处理这种情况)。
  两者的 `logicalId` 会**相同** ⇒ 引擎的 `byLogicalId` 后者覆盖前者,静默丢一个。
- 把设备层编进 `logicalId` 也不行:`logicalId` 是**备份路径的一个路径段**
  (`backups/<workspaceId>/<providerId>[/remote]/<logicalId>`,ADR-54),带斜杠会造出嵌套备份目录。

**当前状态是安全的**:`listSessions` 看不见设备层记录 ⇒ 不会同步 ⇒ `targetPathFor` 也就不会把它们
拍平到顶层。危险的是「只修 listSessions 不修 targetPathFor」,那会在对端造出一份错位的 legacy 副本。
记为 **OQ-24**。

### `.assigned.json` 不纳入同步

新后缀,`CLAUDIAN_RECORD_NAME` 不认。**这一条不是疏忽而是没想清**:
它是「本 conv 归属设备 X」的声明,同步过去会让**对端的 Claudian 把这条会话藏起来**
——恰好与用户启用同步的意图相反。不同步则对端落回 device/unscoped/legacy 阶梯,会话可见。
哪种才对需要先想清楚产品语义,记为 **OQ-25**。

### 「看得见 store 却一条都没准入」的告警

报告 6.4 强烈建议,我同意「静默才是这次最贵的部分」。但它需要一个**在候选集为空时仍然存在的通道**
——而 ADR-62 的 `unprovenOmissions` 挂在 `SessionGroup` 上,零 group 时恰好没有载体,
正是这次的失效形态。需要给 `PassReport` 加一条独立字段并从 adapter 一路接上去。记为 **OQ-26**。

## 五、影响与不影响

| | |
|---|---|
| 受影响 | 2.2.5 之后**新建**的会话,四个 provider 全部 |
| 不受影响 | 存量会话(111 条顶层记录照常);数据安全无风险——只是不同步,本机文件、备份、隔离目录都没动 |
| 趋势 | 每台机器新建的每个对话都会进自己的 `device-<sha>/`,**同步覆盖率随时间单调下降** |
| 用户当前处境 | vault 本身走 iCloud,所以记录文件跨机可见;失效的只是「据此准入并搬运 CLI 会话本体」这一环 |
