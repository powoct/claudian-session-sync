## 不是缺陷

### Dropbox 在推送后改 ctime:多一轮 DEFER

推送方下一轮常见同步夹一侧 `changed-since-last-pass` → `DEFER` / `side-unstable`(Dropbox 上传完成后改了那份的 ctime),再下一轮整读
一次 → `content-identical`,之后 `e1-cache-hit`。续跑里 B1′ ①、B2、Z4、D7、D11、H3 都见到了。代价只是一轮延迟和一次整读:不写入、
不冲突、不饿死(ADR-82 的饥饿额度;B1′ 在上限 3 下 0 行 `budget-exhausted`)。**不能靠忽略 ctime 来省**——那是 ADR-84 否决过的选项 (c)。
已作为预期代价记入 ADR-84 与 testing.md。可选的后续优化:任一侧不稳定时两侧都不读、不计费(代价:截断尾的连续计数暂停;组的计费移到
下一个成员)。

### D12 里本插件建了 `.claudian/sessions/`

按 ADR-78 ③,store 不在时缺的记录照旧 `PULL_NEW`。claudian provider 存在的理由就是 vault 同步带不到 `.claudian` 的设备(Obsidian Sync、
新设备)——那里只能由本插件建出 store,只观察不写就永远同步不了。`*_NEW` 从不替换已有文件;held 的记录在任何判定之前就已结算,
所以一直是 `SKIP_DELETED_HERE`。要改的只是通知措辞(0.3.7)。

### A 上 I1 的 `[no-blob]` 行

A 上 `check r12-pre` 在 `r12b-pre-z` 起有 1 行、`r12b-pre-d11` 起有 2 行 `[no-blob]`,正是预言的两份旧版,两份都在 B 的备份区里找到:

- `codex/2026/10/14/rollout-…-01a139bc-….jsonl` 220,990 B `1e6a2375`:Z1 压缩的就是它(A 仍以 `.zst` 29,014 B `2f345d23` 持有),

快照没开 `--blobs`,所以只能按哈希在别处找到,做不了字节前缀核对。

## 审查发现(1–4 待 0.3.7,不在 0.3.6 里;5 以后)

1. **ADR-78 的一条新残余(审查读代码发现,真机上没见过)。** 重建过的 store 那一轮(若 store 不在的那一轮也采纳新身份,则也包括它),
   一条见证过的记录被判 RESTORE 却没落地——读完之后同步夹那份又变了(O3)、同步夹那份是零字节、或 `PULL_NEW` 执行时失败(A8 前提、
   锁丢失、I/O)——不会结转到下一轮;下一轮按「健康」的 store 判它,可能错判成 `deleted-here` 扣住。同一类:从 0.3.5 升级后的第一轮
   还没有记下 store 身份、恰好 store 不在、而对端恰在那一刻写这条记录。罕见,可经「Bring back conversations deleted on this device」取回,
   两轮后会通知。已作为残余记入 ADR-78。修法:凡缺在本机、判定不是 hold / retired、`PULL_NEW` 没有 APPLIED 的记录,在执行之后按
   `storeRecreated || storeAbsent || recreatedFor` 结转;此后才在 store 不在的那一轮末尾采纳新身份;每种变体各一条测试(只用窄的结转
   必须验红)。
2. **D12 的通知措辞**:claudian 行有 `PULL_NEW` 且 APPLIED 时,把「unavailable」换成「已把 N 条记录恢复进缺失的文件夹」一句。
3. **恢复屏文案**:标题写成「(codex, from the this machine)」(`src/ui/restore-modal.ts` 的 `describeSession`);同步夹那一行的压缩说明
   没说写的是同步夹、会到别的设备;「在 Codex 里打开一次」少了「不发送就退出」。
4. **Codex「cannot tell」通知的措辞**(见下「Codex 的两条观察」),要留余地:「Codex 打开对话时可能加一行」「另一台也续过的话,两份都
   作为冲突保留」;不要叫用户选「Keep the other machine's version」。
5. **不健康的 provider**(之后做):架构 §6 原说「本次跳过」,实际只跳过本机列举——`listReplicaFiles` 走遍所有 adapter,它在同步夹里的
   文件照常规划,新设备上 `PULL_NEW` 可以建出 CLI 的根目录(`node-fs-gateway.ts` 写明了这个意图)。§6 的文字已按实际行为改正;之后把
   HealthReport 拆成「跳过」与「为空」两种。

## Codex 的两条观察

### 打开对话可能会追加一行(n = 1,有混杂)→ OQ-37

Z3 里交互式 `codex resume` 由操作员在伪终端里代跑:只按回车接受了首次的目录信任提示(脚本在提示还在缓冲时又多按了一次),其余什么都没输入,Ctrl+C 退出。
还原出的 `.jsonl` 比压缩前多 2,699 B、多 1 条记录(110,352 → 113,051 B,35 条)。混杂因素有三:信任提示、多出的回车、这次 resume 起的
托管 app-server 守护进程。exec 路径的还原不加记录:`01a13d30` 压缩后经 `codex exec resume … "continue"` 还原,终态 34 条,与没压缩过、
同样只续了一轮的会话相同。

若属实,后果是:同步夹那份确实是压缩内容的延续、但插件证明不了时(基线丢了;或帧头不声明原长且 mtime 动过——实际中没见过,608/608 个
真实压缩件都声明了原长),「打开一次、不发送就退出」会以 `CONFLICT`(两份都保留)收场,而不是拉取;同步夹那份等于压缩内容时(ADR-83
残余 ⑧,A 的 17 条)以 `PUSH_OVERWRITE` 收场,无害。**两种都不丢数据。** Z3 自己的 `CONFLICT` 完全由刻意造的那一轮本地续接解释,与这
一行无关。

文档处理:ADR-83 新增残余 ⑨(按上面的保留措辞);架构 §6 里 codex 0.146.1「只读 resume 不写」补一句「≥ 0.158 未复核;第 12 轮续跑有一次
交互式 TUI resume +1 条(2,699 B)的混杂观察;exec 路径还原不加」;通知措辞改到 0.3.7。新开 **OQ-37**:打开一个 Codex 对话会不会追加?
探针设计:预先信任好的 cwd,零按键;记下托管守护进程在不在、是什么版本(A 上现在跑着 0.162.1 的守护进程,宜在 B 上做);包括 Claudian
2.3.20 里选中不发送;只记大小与记录条数的变化,不读内容。之后补一条测试项 Z3b:基线丢失、本地没有续接。

### OQ-31(压缩从哪来)的新证据

- A 上 ChatGPT.app 自带的 `codex app-server`(在 `ChatGPT.app/Contents/Resources/codex-cli/…` 里)一直在跑,与 Obsidian、Claudian、PATH 上的
  CLI 都无关——**首要候选**。

  已记:`rollout/compress` 不看那个开关)。
